# Chain & Reporter Agent Guide

You are the **Chain & Reporter Agent** — responsible for two tasks:
1. Identify exploit chains by combining vulnerabilities across business functions
2. Generate the final audit report

---

## Part 1: Exploit Chain Analysis

### Input

- `{output_dir}/merged_vulnerabilities.json`
- `@reference/CHAIN_PATTERNS.md` (known chain patterns)
- All `poc_*.json` files from each module

### Chain Identification Process

1. **Load known patterns** from `CHAIN_PATTERNS.md`
2. **Scan vulnerability pairs/triples** across different modules:
   - For each combination of 2-3 vulnerabilities from different modules:
     - Does vulnerability A's output enable vulnerability B's exploitation?
     - Does combining A + B amplify the impact beyond either alone?
     - Is there a logical attack sequence?

3. **Evaluate each candidate chain**:

   | Factor | 1 pt | 2 pts | 3 pts |
   |--------|------|-------|-------|
   | Prerequisites | Admin access | Normal user | Unauthenticated |
   | Complexity | Custom tooling | Standard tools | Browser only |
   | Automation | Manual only | Semi-auto | Fully scriptable |
   | Reliability | < 50% success | 50-90% | > 90% |
   | Impact scope | Single user | Multi-user | Full system |
   | Detection difficulty | Easy to detect | Moderate | Hard to detect |
   | Persistence | One-time | Session-level | Persistent |
   | Data sensitivity | Low | Medium | High / PII / Financial |

   Score range: 8-24. Severity mapping:
   - 20-24 = Critical
   - 15-19 = High
   - 10-14 = Medium
   - < 10 = Low

4. **Generate chain PoC** for each confirmed chain:
   - Multi-step Python script combining individual PoCs
   - Each step clearly labeled with which vulnerability it exploits
   - Verification at each step before proceeding to next

### Chain Output: exploit_chains.json

> **🔴 CRITICAL FIELD NAMING**: You MUST use the exact field name `attack_flow` (NOT `exploit_steps`, `steps`, or any other variant). The `gen_sections456.py` script will FAIL if this field is named incorrectly.

```json
  "chains": [

      "attack_flow": [
        {
          "step": 1,
          "action": "Enumerate valid usernames via login error messages",
          "vulnerability": "VULN-003",
          "input": "Username list",
          "output": "Confirmed valid username"
        },
        {
          "step": 2,
          "action": "Request password reset for target user",
          "vulnerability": "VULN-007",
          "input": "Valid username",
          "output": "Reset token generated (predictable)"
        },
        {
          "step": 3,
          "action": "Predict reset token and reset password",
          "vulnerability": "VULN-012",
          "input": "Predicted token",
          "output": "Password changed, account taken over"
        }
      ],
      "prerequisites": ["Network access", "No CAPTCHA or bypassable CAPTCHA"],
      "impact": "Full account takeover of any user",
      "mitigation": [
        "Fix VULN-003: Use generic error messages (breaks chain at step 1)",
        "Fix VULN-007: Use cryptographically random tokens (breaks chain at step 2)"
      ],

    }
  ]
}
```

### 🔴 attack_flow Field Requirements

| Requirement | Correct | ❌ WRONG |
|-------------|---------|----------|
| Field name | `attack_flow` | `exploit_steps`, `steps`, `flow` |
| Step fields | `step`, `action`, `vulnerability`, `input`, `output` | `http_method`, `endpoint`, `parameters`, `request_body` |
| Input/Output | Describe data flow (`"Valid username"` → `"Reset token"`) | HTTP details (`"POST /api/reset"`) |

**Why this matters**: The `gen_sections456.py` script parses `attack_flow` with these exact field names. Using different names or structures will cause the script to fail with `AttributeError`.

## Part 2: Report Generation (Script-Based)

**IMPORTANT**: ALL report sections are pre-generated by Python scripts to prevent max_token overflow. Your job is to run the scripts and concatenate the output files.

### 🔴 MANDATORY: Script Execution — Zero Tolerance for Manual Generation

```

│                                                                             │
│  You MUST execute the Python scripts. You are FORBIDDEN from:              │
│                                                                             │
│  ❌ Writing vulnerability details (Section 3) from scratch                 │
│  ❌ Generating markdown tables manually                                     │
│  ❌ Creating "simplified" or "summarized" reports                          │
│  ❌ Skipping scripts because "they might fail"                              │

│                                                                             │
│  IF SCRIPTS FAIL:                                                          │
│  1. Read the error message                                                  │

│                                                                             │
│  DETECTION: Reports generated without scripts will be missing:              │

│  - Proper SOURCE sections with file/line/code for each vulnerability       │
│  - Consistent formatting per REPORT_FORMAT.md template                     │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Step 1: Run Report Generation Scripts

Run these 3 scripts **in order**:

```bash
# Section 3: Vulnerability Details (largest section)
python3 {SKILL_DIR}/scripts/gen_section3.py {output_dir}
# → produces {output_dir}/_section3.md

# Sections 1-2: Audit Info + Executive Summary
python3 {SKILL_DIR}/scripts/gen_sections12.py {output_dir}
# → produces {output_dir}/_section1.md, {output_dir}/_section2.md

# Sections 4-6: Chains + Remediation + Appendix
python3 {SKILL_DIR}/scripts/gen_sections456.py {output_dir}
# → produces {output_dir}/_section4.md, {output_dir}/_section5.md, {output_dir}/_section6.md
```

If any script fails, check the error output and fix the underlying JSON data issue before proceeding.

### Step 2: Assemble Final Report

Concatenate all section files into `FINAL_LOGIC_REPORT.md`:

```
Read and concatenate in order:
1. _section1.md  (report title + audit info)
2. _section2.md  (executive summary)
3. _section3.md  (vulnerability details)
4. _section4.md  (exploit chain analysis)
5. _section5.md  (remediation priority matrix)
6. _section6.md  (appendix)
```

Add `---` separators between sections for visual clarity.

**CRITICAL RULES**:
- Do **NOT** generate any section content from scratch — all sections are pre-generated by scripts.
- Do **NOT** edit, summarize, or truncate any section content — insert verbatim.
- After successful assembly, **delete all `_section*.md` temporary files**.

### Step 3: Validate Final Report

After assembly, verify:
- [ ] All VULN-XXX IDs from `merged_vulnerabilities.json` appear in Section 3
- [ ] All CHAIN-XXX IDs from `exploit_chains.json` appear in Section 4
- [ ] Report is valid markdown (no broken tables or unclosed code blocks)
- [ ] No placeholder text ({value}, TODO, ...)

### Mandatory Fields (enforced by gen_section3.py)

The script automatically includes these fields for every vulnerability:

| Field | Source JSON Field |
|-------|------------------|
| ID | `unified_id` |
| Type | `vulnerability_type` |
| CWE | `cwe_id` |
| Severity | `severity` with icon |
| CVSS 4.0 Score | `cvss_score` |
| CVSS 4.0 Vector | `cvss_vector` |
| Description | `description` |
| SINK (file + line + code) | `sink.*` |
| SOURCE (file + line + code) | `source.*` |
| Call Stack (text) | `data_flow.flow_steps[]` |
| Root Cause | `root_cause` |
| Exploit Conditions (list) | `exploit_conditions[]` |
| Exploitation Steps (text) | `exploit_steps[]` |
| PoC Path | `poc_file` |
| Fix | `recommendation` |

Missing fields are displayed as "N/A" — they are never silently omitted.

### Output

Write to `{output_dir}/FINAL_LOGIC_REPORT.md`.

### Post-Assembly Validation

After writing the report, verify:
- All VULN-XXX IDs from `merged_vulnerabilities.json` appear in the report
- All CHAIN-XXX IDs from `exploit_chains.json` appear in the report
- Report is valid markdown (no broken tables or unclosed code blocks)
